# FL2 / FL3: preparation, installation and verification

[Home](../../README.md) · [简体中文](../zh-CN/fl23.md) · [Developer guide](development.md)

This repair branch targets **Sony A7C II / ILCE-7CM2 firmware 2.01**. It has offline software evidence; no new physical installation, boot, photo/video or recovery acceptance is claimed. Upstream Release downloads do not contain unmerged branch changes.

## 1. Check the camera and workflow

Confirm **2.01** on the camera's version screen. The compatibility command records the version you enter; it does not query the installed version automatically. Keep sufficient continuous power and a data-capable USB connection. Installation requires the actual battery percentage to be at least 50%.

Use explicit `prepare` → `install` → `verify` for this branch, including when LUTs already exist. It preserves current LUT slots/dispatch and plans the reviewed FL23 gamma changes over the actual programs. Conflicting bytes stop preparation. The CLI prints a warning about other firmware modifications before installation.

Double-clicking `FL23.cmd` still opens the refactored GUI. Its `check`, `backup`, automatic-install and legacy restore routes use the earlier stock-only workflow. Its backup button is **not** the explicit compatibility `prepare` command. Mixed-feature rollback uses independent [Recovery](recovery.md).

## 2. Prepare the computer

Use Windows and 64-bit Python 3.10+. The GUI also needs Tkinter. The launcher prepares Python/device/compiler dependencies; see [setup](manual.md) or the [developer environment](development.md#4-development-environment).

From the complete source checkout, these commands do not connect to a camera:

```text
.\FL23.cmd --help
.\FL23.cmd --check
.\FL23.cmd --setup-only
.\FL23.cmd check-package
```

The compatibility workflow needs the complete checkout or a bundle containing it, including `dev/windows/` and `src/looks/`. Do not copy a launcher out of its directory tree. The old v2.2-preview.1 release and current source branch are different revisions.

## 3. Connect the camera and prepare USB drivers

Connect one supported body and choose **Mass Storage / MSC**, then close other camera tools. The normal identity is `054C:0E8A`; authentication can re-enumerate it as service identity `054C:0336`.

On Windows, the current device layer accepts WinUSB, libusbK or libusb0. Both identities need usable drivers. If using [Zadig](https://zadig.akeo.ie/), identify the exact camera VID/PID; the service identity may only appear after first authentication. A working normal driver does not prove the service driver works.

### First driver replacement disconnects / “Check the connected device”

A replacement driver can remove the ordinary camera drive from Explorer. The screen message alone does not identify the cause. Preserve the failed workspace/logs and check which USB identity is present before changing a driver. If first preparation stops solely because 0336 has no driver, end the operation, configure that identity and prepare again only after the prior result is understood. The legacy `check` command authenticates to service mode; it is not an offline check. Do not repeatedly click Install or assume a timeout means a driver needs reinstalling.

The repaired session checks the USB product string, authenticates directly and then binds the AP serial. Storage readiness and `getCameraInfo` are not prerequisites. An ambiguous authentication or transfer is not automatically retried.

## 4. Capture backups and build the candidate

Choose a new empty workspace and an independent empty backup directory. Prefer separate drives for the copies. They cannot contain each other. Replace the example paths with your own:

```text
.\FL23.cmd prepare --firmware-version 2.01 --workspace "D:/CameraWork-A7C2-01" --backup-copy "E:/CameraBackup-A7C2-01"
```

This connects to the camera, reads programs/settings/resources, saves both originals and an independent checkpoint, builds the per-body candidate and executes temporary native preflight. It does not install the program or save look settings. Require a successful `prepared` phase. If the current FL23 is already enabled, the tool retains that state without reinstalling it.

Retain both complete directories, `state.json`, evidence and `checkpoint.private.zip`. A copied candidate or manifest alone is not a recoverable body backup.

## 5. Install the prepared transition

Use the same workspace and the **actual** battery percentage; `82` is only an example:

```text
.\FL23.cmd install --workspace "D:/CameraWork-A7C2-01" --battery-percent 82
```

The tool checks body identity, fresh complete programs, target settings and unrelated unsaved recipes before writing. It then writes the planned windows, reads back complete files, saves/verifies selected color settings and handles the retained boot image. Keep power and USB connected until all I/O finishes.

A failure or unknown result requires diagnosis using the preserved evidence. Do not edit the phase or replay an installer to force completion.

## 6. Cold reload and verify

Only after successful `installed_pending_cold_start` and the end of all I/O, disconnect USB/other power, shut down normally, wait for the access lamp and remove the battery for at least one minute. Restart and check menu names, no-shutter preview switching, new FL2/FL3/ST captures and playback. Reconnect MSC:

```text
.\FL23.cmd verify --workspace "D:/CameraWork-A7C2-01"
```

Verification checks current FL23 patches, saved parameters and loaded AP fragments, allowing a later supported LUT installation. It does not reinstall. Record actual photo/video observations separately from byte-readback results.

## 7. Complete rollback

Use independent [Recovery](recovery.md) with the original complete checkpoint or supported legacy backup. It does not require a LUT job. The retained stock-only FL23 restore helper is not for a combined FL23/LUT image. Do not copy another body's settings/calibration to this body.

## 8. What has been verified

See [development verification](development.md#6-offline-verification) and the [changelog](changelog.md). Both install orders, gamma routing, slot undo and checkpoint rollback have offline evidence using official program bytes and simulated settings. That does not establish real USB reliability, boot safety, image quality, long-term stability or power-loss recovery. Historical one-body results belong to their original builds.
